# CMND Linux 0.8.0 — Ubuntu 24.04 Test Guide

This guide is for the isolated **0.8.0 development line** only. The published
`v0.7.1` release remains the frozen working reference and is not modified by
0.8 development.

## Test target

Use a disposable or dedicated Ubuntu Server **24.04 LTS amd64** host.

Recommended minimums:

- 6 GiB RAM
- 40 GiB disk, with at least 10 GiB free under `/var/lib`
- stable IPv4 address on the TV-management LAN
- working DNS and Internet access during dependency/container preparation
- sudo/root access

Do not begin with a machine that already contains a CMND deployment. Existing
Apache/nginx, Docker, and MySQL/MariaDB services are acceptable because 0.8
inventories them and plans coexistence before activation.

## What the 0.8 APT bundle contains

The test bundle contains four Debian packages:

```text
linux-cmnd_0.8.0_amd64.deb
cmnd-vendor-759_7.5.9-1_all.deb
cmnd-tomcat9_9.0.121-1_all.deb
cmnd-linux_0.8.0_all.deb
```

`cmnd-linux` is the user-facing installation package. It requires the exact
matching tooling package, the hash-verified Philips CMND 7.5.9 inputs, and the
pinned Tomcat 9.0.121 archive.

The Philips inputs remain outside Git source history. The vendor package is
generated only from the exact input set already verified by the project.

## Before activation

After the tooling package is installed, these commands are read-only:

```sh
sudo cmndctl environment
sudo cmndctl plan-install
```

The environment report inventories web/database/runtime services and listeners.
The plan does not modify the host.

The planner preserves unrelated listeners. CMND prefers its historical ports
when free and moves only CMND-owned listeners when necessary:

- Tomcat HTTP: 8080
- Tomcat HTTPS: 8443
- SmartCMS/Apache HTTP: 8082
- SmartCMS/Apache HTTPS: 8444
- database: 3306
- private PHP-FPM: 9000
- private management UI: 9078

## Installing the four-package test bundle

From the directory containing all four packages:

```sh
sudo apt update
sudo apt install \
  ./linux-cmnd_0.8.0_amd64.deb \
  ./cmnd-vendor-759_7.5.9-1_all.deb \
  ./cmnd-tomcat9_9.0.121-1_all.deb \
  ./cmnd-linux_0.8.0_all.deb
```

The package configuration asks for:

1. Server IPv4 address. `auto` prefers the IPv4 source selected by the host's
   default route.
2. Database mode:
   - `auto` — reuse an existing database only if it already passes the strict
     shared-server gate; otherwise use the isolated MySQL 5.7 runtime.
   - `existing` — require a compatible existing database and refuse fallback.
   - `isolated` — leave any host database alone and use the qualified isolated
     MySQL 5.7 runtime.
3. Database administrator user/password only when required for an existing
   database. The password is transferred through a root-only temporary file and
   cleared from debconf after the activation attempt.
4. Apache mode:
   - `auto` — use an already-running supported Debian/Ubuntu Apache service via
     one CMND-owned configuration fragment; otherwise use standalone CMND Apache.
   - `host` — require host Apache.
   - `standalone` — do not attach CMND to the host Apache service.
5. Explicit acceptance of the legacy PHP 5.6 / MySQL 5.7 compatibility profile.

If legacy-runtime acceptance is not granted, the packages install but CMND is
not activated. Activation can then be revisited through package reconfiguration.

## Existing MySQL/MariaDB safety

0.8 does **not** change server-wide database settings to make an unrelated
database service compatible.

Automatic shared-database reuse currently requires the already-qualified
MySQL 5.7 family and the reviewed global profile, including:

- `lower_case_table_names=1`
- `event_scheduler=ON`
- `local_infile=OFF`
- reviewed `sql_mode=NO_ENGINE_SUBSTITUTION`
- server not read-only
- no existing CMND schema/user namespace

MariaDB and MySQL 8 remain unqualified as shared CMND databases. In `auto`
mode they are preserved and CMND uses its isolated database fallback.

A failed fresh shared-database activation removes only the fixed CMND schemas and
application accounts that the same fresh transaction created. It does not alter
unrelated schemas/users.

## Existing Apache/nginx safety

When reusing a supported host Apache installation, CMND owns only:

```text
/etc/apache2/conf-available/cmnd-linux.conf
```

The installer does not replace `apache2.conf`, `ports.conf`, or unrelated
sites. It config-tests Apache before relying on the fragment and removes its own
fragment on a failed attach.

An existing nginx installation is preserved. If Apache is not being reused,
CMND runs its own standalone Apache process on CMND-owned listeners.

## First-install network safety

A fresh APT-generated configuration starts with:

```toml
[safety]
permitted_ranges = ["127.0.0.0/8"]

[tv]
allowlist = []
```

Installing CMND does not authorize a physical TV for write operations. Keep the
TV allowlist empty until server/browser qualification has passed and the first
physical-TV procedure is intentionally started.

## Expected first-start duration

The Java applications can have a long cold start. Previous qualification on a
6 GiB VM observed startup taking roughly 11 minutes. Do not assume installation
failed only because vendor pages are not immediately available.

## Verification after installation

Start with:

```sh
sudo cmndctl environment
sudo cmndctl native-health --seconds 900
sudo systemctl --no-pager --full status \
  cmnd-egress.service \
  cmnd-php.service \
  cmnd-tomcat.service \
  cmnd-admin.service
```

If the isolated database/standalone Apache path was selected, also check:

```sh
sudo systemctl --no-pager --full status cmnd-mysql.service cmnd-apache.service
```

If host Apache was selected:

```sh
sudo apache2ctl configtest
sudo systemctl --no-pager --full status apache2.service
```

Confirm the deployment marker:

```sh
sudo cat /etc/cmnd/deployment.json
```

A successful APT-managed activation should identify itself as
`linux-cmnd-apt` with state `active`.

## Initial administrator credentials

The first generated administrator credentials are root-readable at:

```text
/var/lib/cmnd-deployment/initial-admin.json
```

Treat this file as a secret. Do not paste it into issue reports or commit it.

## Evidence and troubleshooting

Useful state/log locations include:

```text
/etc/cmnd/
/var/lib/cmnd-deployment/
/var/log/cmnd/
/var/cache/linux-cmnd/bootstrap/php-build.log
```

If activation fails, preserve `/var/lib/cmnd-deployment` and the private logs
before changing anything. A failed deployment intentionally stops CMND
application services rather than trying to hide partial state.

## Package removal

Removing `cmnd-linux` stops/disables CMND-owned services and detaches the
CMND-owned host-Apache fragment when present. Package removal deliberately
retains CMND data, configuration, certificates, logs and database state.

Do not use package removal as a data-erasure operation.

## Scope of this test

For 0.8 right now:

- Ubuntu 24.04 amd64 is the primary test target.
- Ubuntu 22.04/Python 3.10 is an informational compatibility lane, not a supported
  APT target yet.
- Ubuntu 26.04 remains unqualified.
- Docker/Compose rendering exists but host-network physical-TV discovery/control
  is not yet qualified.
- RF/DekTec/modulator and remaining Windows-only MGate-dependent workflows are
  not implied to be complete by a successful APT installation.

A successful package/source CI run is not a replacement for this clean-host
runtime test with the actual vendor payload.
