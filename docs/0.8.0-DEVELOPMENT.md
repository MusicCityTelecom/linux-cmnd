# Linux CMND 0.8.0 development line

## Baseline

`develop/0.8.0` was created directly from the immutable `v0.7.1` tag. Version 0.7.1 remains the frozen working reference and must not be modified, republished, or used as a development branch.

The 0.8.0 line begins as an architectural copy of 0.7.1. Later fixes from `main` are imported only by deliberate review/cherry-pick after proving they are appropriate for 0.8.0.

## Primary goals

1. Preserve the existing Philips CMND application/runtime behavior that is already qualified on Linux.
2. Add an environment-inventory layer before any installer mutation.
3. Add coexistence-aware native installation for hosts that may already run Apache, MySQL/MariaDB, Java, PHP, Docker, or other services.
4. Never overwrite unrelated sites, databases, users, credentials, configuration, listeners, or service definitions.
5. Detect port collisions before activation. Prefer the current CMND ports when free; otherwise select reviewed alternatives and regenerate every CMND-owned reference consistently.
6. Reuse a compatible existing database service where practical. Prefer local administrative socket authentication when available; request database administrator credentials only when necessary, never persist the administrator password, and create CMND-specific application users with generated credentials.
7. Reuse existing Apache through CMND-owned configuration fragments when safe; otherwise keep CMND isolated rather than replacing host configuration.
8. Provide a signed Ubuntu APT repository so the intended operator path becomes `sudo apt install cmnd-linux` after repository enrollment.
9. Qualify Ubuntu 24.04 first, then separately qualify 22.04 and 26.04 rather than assuming compatibility.
10. Add a production-oriented Docker/Compose deployment path that reuses the same vendor payload staging, rendering, secrets, schemas, validation, and application configuration logic as the native installer.

## Safety invariants

- No development change may alter the `v0.7.1` tag or published 0.7.1 release assets.
- Fresh-install and upgrade logic must be idempotent or fail closed before destructive work.
- Existing customer/application data must be preserved.
- Existing database services are inventoried and compatibility-checked before use.
- Existing web-server sites and global configuration are preserved; CMND changes are isolated to CMND-owned files/fragments wherever possible.
- Database administrator credentials are transient input only and are never written to CMND configuration or logs.
- Vendor application inputs remain hash-pinned and binaries remain outside Git source history.
- No live TV contact, host-network changes, or production deployment is performed without explicit operator approval.

## Initial milestones

### M0 - frozen fork and regression baseline

- Branch directly from `v0.7.1`.
- Mark development version `0.8.0-dev1`.
- Run the complete existing test suite unchanged and record results before feature development.

### M1 - read-only environment inventory

Add a detector that reports, without modifying the host:

- supported OS/release/architecture;
- Apache/nginx presence, version, enabled state, active configuration paths and listeners;
- MySQL/MariaDB presence, version, socket/host/port and administrative authentication options;
- Java/JAVA_HOME and Tomcat installations;
- Docker/Compose presence and running containers;
- PHP/FPM presence and listeners;
- occupied CMND/default/private ports and owning processes where available;
- existing Linux CMND package/runtime/state;
- disk, memory and package-manager readiness.

The detector must return machine-readable data suitable for installer planning and a human-readable `cmndctl environment` report.

### M2 - installation planner

Convert inventory into an explicit plan before mutation. The planner chooses reuse/install/isolate actions for each dependency, resolves CMND-owned ports, and displays any operation that would touch existing services. Planning itself performs no changes.

### M3 - coexistence-aware native activation

Implement and test the approved plan with rollback/fail-closed behavior, CMND-specific database identities and isolated Apache configuration.

### M4 - APT repository path

Build/sign repository metadata and validate clean install, upgrade, reinstall and removal behavior through APT.

### M5 - Docker deployment

Build Compose/runtime packaging from the same application staging inputs and determine/qualify the networking mode required for Philips TV discovery/management.

## Qualification matrix

At minimum, 0.8.0 must be exercised on disposable systems for:

- clean supported Ubuntu installation;
- pre-existing Apache with unrelated sites;
- pre-existing compatible MariaDB/MySQL with unrelated schemas/users;
- local socket-auth and password-auth database administration;
- occupied 8080/8443/8082/8444/3306 listeners;
- pre-existing Docker installation/containers;
- reboot persistence;
- package upgrade and rollback/recovery;
- uninstall/reinstall without deleting retained CMND data;
- Docker/Compose deployment;
- Ubuntu 22.04, 24.04 and 26.04 as separately reported qualification targets.

Passing simulator or source tests does not imply browser, runtime, physical-TV or production qualification.
